# DESIGN: устройство среды

## 1. Процессы и границы доверия

```
┌──────────────── процесс оценщика (python -m auditenv.grader.service) ────────────────┐
│ генератор эпизодов (seed + config + секрет) → truth/provenance в памяти              │
│ matcher + награда, журнал оценщика, oracle (только при allow_oracle)                 │
└───────────────▲──────────────── строки JSON через stdin/stdout ──────────────────────┘
                │ open / grade (1 раз на эпизод) / oracle / finalize / results
┌───────────────┴──── процесс среды ───────────────┐      ┌──── процесс агента (опц.) ────┐
│ AuditEnv: reset/step, ReadOnlyStore открытых      │◄────►│ agent_host: только JSON-      │
│ записей, курсоры, калькулятор. Нет truth и seed.  │ JSON │ наблюдения/действия, нет       │
└───────────────────────────────────────────────────┘      │ клиента оценщика и секрета    │
                                                           └────────────────────────────────┘
```
* Среда **не генерирует** эпизоды и не читает диск: открытые файлы приходят от оценщика. `seed` не сохраняется в объекте среды.
* Протокол — только JSON, без pickle. Оценка принимается один раз на эпизод. В eval-режиме политика получает `reward=0`, `info={}`, а итоги доступны только после `finalize` (после него новые эпизоды не открываются).
* На закрытом прогоне эпизоды генерируются в памяти оценщика из `closed_episodes_file` и `secret_file`, эталон не касается диска. Закрытый эпизод открывается только в eval и только один раз за прогон, поэтому прощупать эталон повторными оценками нельзя. Открытые train/dev лежат в `episodes/`; их эталон хранится отдельно, в `grader_data/`.

## 2. Генератор: история → документы → ошибки

1. **Мир** (`generator/world.py`). Компания (base ∈ {KZT, USD, EUR, …}, фиксированное смещение UTC), месячный период, клиенты в разных валютах и часовых поясах, поставщики, курсы FX на **каждый** календарный день (Decimal-случайное блуждание, строки). Из мира строятся:
   * счета с `line_items` (`qty × unit = amount`, `Σ = total`), включая прошлый период (входящее сальдо) и следующий (видны, но не проводятся);
   * платежи: полные, разбитые, частичные, переплаты, пакетные, предоплаты и возвраты;
   * расходы.
2. **Проводки** (`post_all`). Строятся из документов и «бухгалтерских решений» (`bookings`). Книга ведётся в base. Правила:
   * курс — на локальную дату момента документа в часовом поясе компании;
   * AR погашается по историческому курсу, а платёж, закрывающий счёт, снимает остаток;
   * разница уходит в `fx_gain_loss`, нераспределённое — в `customer_advances`.
   Каждая запись сбалансирована. `row_id` = хеш(ключ эпизода, документ, роль строки), поэтому после перепроводки неизменённые строки сохраняют ID.
3. **Мутации** (`generator/mutations.py`). Каждая мутация меняет решение или добавляет ошибочно проведённый документ, затем делается перепроводка. Причинное изменение «было → стало» пишется в provenance, дифф открытых записей до/после вычисляется сравнением рендеров. `truth.json` строится **только** из записей мутаций.
4. **ГПСЧ** (`common/drbg.py`) — SHA-256 в режиме счётчика, с независимыми подпотоками world/ids/mutations/issue_ids. Причина отказа от Mersenne Twister: его состояние восстанавливается по выходам, видимым в открытых ID и суммах, а с открытым генератором это даёт «чистый» мир и дифф с мутациями. float-методы запрещены. Ключ эпизода = SHA-256(версия, секрет, seed, канонический config).

| тип | варианты | канонические `affected_ids` | сумма (≥0) | допустимые наборы доказательств |
|---|---|---|---|---|
| `duplicate_invoice` | копия в периоде; копия из следующего периода | оба `invoice_id` | `total_minor`, валюта счёта | {оба счёта + любая из 4 проводок AR/revenue} |
| `missing_or_partial_allocation` | `invoice_refs` = null; распределено меньше remittance | `[invoice_id, payment_id]` | remittance − распределено, валюта платежа | {счёт, платёж, строка `customer_advances`} |
| `fx_wrong_date_or_rate` | наивная дата; сдвиг на ±1–3 дня; дата `due_at`; курс чужой валюты | `[id документа]` | \|проведено − верно\|, base | {документ, строка AR или revenue (у счёта) либо bank (у платежа), `fx:<дата>:<src>:<base>`} |
| `period_cutoff_error` | следующий период проведён в этом (часовой пояс проигнорирован / начислено на закрытии); прошлый период проведён как новый | `[invoice_id]` | сумма проводки, base | {счёт, строка AR или revenue} |

**Взаимодействия**, явно описанные в `truth.interactions`:
* `partial_fx_boundary` — платёж в иностранной валюте за несколько часов до конца периода, его наивная дата уже в следующем месяце. Внедряются частичное распределение (сумма в валюте платежа) и курс по наивной дате (сумма в base). Получаются 2 issue на одном платеже, суммы в разных валютах и не гасят друг друга.
* `duplicate_cutoff` — дубль счёта, выпущенный уже в следующем периоде, но проведённый в этом. Получаются 2 issue.

**Отвлекающие случаи** создаются в мире как корректные данные (9 видов):
* еженедельные подписки с одинаковой суммой;
* одна сумма при разных строках счёта;
* разбитые платежи;
* частичная оплата при открытом счёте;
* переплата в авансы;
* пакетный платёж;
* предоплата и её возврат;
* счета у границы периода, у которых наивная дата вне периода;
* счета следующего периода, у которых наивная дата внутри периода;
* иностранные платежи у конца периода.

## 3. Среда (раздел 04)

* Наблюдение всегда имеет форму `{result, error, steps_remaining}`. Первое — `{task, manifest, policy, tools, budget}`.
* Действия: `list_records` (≤50 строк; курсор = base64(`table:offset:HMAC`), стабилен между reset и не раскрывает ничего, кроме позиции), `get_record` (по первичному ID; у счетов и платежей принимается и `doc_id`; у курса ключ `fx:<date>:<src>:<tgt>`), `get_document` (единственный источник remittance advice, PO и memo), `calculator` (ast с белым списком, только Decimal, лимиты длины, узлов, глубины и величины), `submit`.
* Ошибки — фиксированные коды с короткими русскими сообщениями, без ID, путей и стектрейсов. Каждая ошибка расходует шаг.
* Лимиты: 100 шагов включая submit и 60 с wall-clock, лимит времени проверяется до действия. При превышении — `truncated=true` и оценка пустого ответа. Шаг после завершения возвращает `episode_finished` без расхода шага и без переоценки.
* `inspection_steps` — все шаги до submit, включая ошибочные, без самого submit. При truncation — число сделанных шагов.

## 4. Matcher и награда (раздел 05, код открыт: `grader/matcher.py`, `grader/reward.py`)

* **Нормализация.** Строгая схема: лишние ключи, float/str/bool в сумме, отрицательная сумма, превышение лимитов 30/10/1000, тип вне enum, чужой `episode_id` → неверная структура (−1 и запись в журнал). `doc_id` заменяется на ID записи; `affected_ids` и `evidence_ids` превращаются в множества; валюта приводится к верхнему регистру.
* **TP** требует одновременно: тот же тип, канонические `affected_ids`, `|сумма − эталон| ≤ tolerance_minor = 0`, ту же валюту и `evidence_ids` ⊇ одного из допустимых наборов. Текст explanation не влияет.
* **Сопоставление** — максимальное паросочетание (алгоритм Куна): выводы перебираются по индексу, эталон по `issue_id`. Размер паросочетания не зависит от порядка, поэтому повторы становятся FP.
* **Награда** считается точно, через `Fraction`, наружу отдаётся float: `clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`. Краевые случаи F1 — строго по PDF.

## 5. Независимый валидатор (`generator/validate.py`)

Валидатор не импортирует генератор: конвертация, границы периода и правила учёта переписаны заново по тексту policy. Он проверяет:
* схемы и manifest (счётчики и SHA-256 файлов);
* состояние «до», восстановленное из `provenance.diff`: детекторы не находят ни ошибок, ни противоречий;
* состояние «после»: детекторы находят **ровно** эталон (тип, ID, сумма, валюта);
* каждый набор доказательств сам по себе пересчитывает ту же сумму;
* отвлекающие случаи чисты, взаимодействия корректны.

Сверх этого: самопроверка на испорченных входах (`test_validator_detects_corruption`) и статистические анти-трюки (позиция, порядок ID, круглые суммы).

## 6. Assumptions (выбраны самые строгие разумные трактовки)

1. Книга ведётся в base, поле `currency` всех строк равно base; сравнивать валюты без конвертации нельзя.
2. Дата курса — локальная дата момента документа в смещении компании. Период — `[start 00:00, end+1 00:00)` в том же смещении.
3. Сумма в выводе — модуль расхождения (≥0); знак не оценивается.
4. Для дубля в `affected_ids` указываются оба счёта, потому что «оригинал» по данным не отличим от копии.
5. Remittance advice из `get_document` — факт, по которому проверяется распределение.
6. Неизвестные ID в выводе считаются не ошибкой структуры, а FP: все ID открыты, существование ничего не раскрывает.
7. Oracle отправляет ответ без осмотра (k = 0), поэтому максимум награды равен 1. Его ответ не выходит из процесса оценщика, а в траекториях action заменён заглушкой.
8. `documents.jsonl` — дополнительный открытый файл за `get_document`; таблицы раздела 03 совпадают со схемой буквально.

## 7. Честные ограничения

* **Модель учёта упрощена.** Только дебиторка (продажи) и расходы без документов. Нет кредиторки, налогов, кредит-нот и частичных возвратов по счетам; период — один месяц.
* **Cutoff внедряется только для счетов.** Cutoff платежей валидатор умеет детектировать, но генератор его не создаёт.
* **Часовые пояса — фиксированные смещения**, без DST и tzdata. Курсы даются только парами foreign→base на каждый день: правило «ближайший предыдущий рабочий день» не моделируется.
* **Граница изоляции.** Жёсткая граница — отдельный процесс агента (`agent_host`). Базовые политики работают в процессе среды и считаются доверенным кодом. Злонамеренный in-process-код увидит только открытые записи: эталона там нет, а oracle отключён, кроме прогона oracle.
* **Эталон train/dev лежит на диске** в `grader_data/` — это открытые сплиты. Закрытый эталон существует только в памяти оценщика. Без `secret_file` маленькие seed перебираются открытым генератором, поэтому на закрытом прогоне секрет обязателен.
* **Docker-образ в нашей песочнице не собран**: Docker Hub закрыт прокси. Проверка выполнена в чистом `git clone` + свежем venv Python 3.11 — результат зелёный, артефакты побайтово совпали.
* **Детерминизм — в пределах одной версии Python** (проверено на 3.11, разный `PYTHONHASHSEED`, разные процессы).
* **Названия компаний вымышленные**, но составлены из словарей и могут случайно совпасть с реальными. Суммы, документы и люди синтетические, реальных данных нет.
* **Особенности правил PDF.** Бездействие до truncation на чистых книгах даёт 0.8. Средние P/R у oracle меньше 1 на чистых эпизодах из-за правила нулевого знаменателя.
* **Анти-трюковые тесты статистические** (60 эпизодов) и не доказывают отсутствие любых корреляций. `simple_reconciler` — наш базовый алгоритм, а не алгоритм организаторов.
* **Train-режим по природе RL — канал информации.** Повторяя один и тот же открытый seed, можно подбирать ответ по награде. Поэтому закрытые эпизоды доступны только в eval и один раз.
* **Награда не доказывает пригодность для реального аудита** (раздел 05 PDF). Обучение весов не проводилось, заявлений об улучшении модели нет.
