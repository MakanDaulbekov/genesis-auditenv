## P1

### F1. ID в формате жюри, не проходящем `ID_RE`, превращают честный ответ в −1

`grader/matcher.py`: `ID_RE = ^[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}$`; каждый ID в `affected_ids`/`evidence_ids`, не прошедший
шаблон, даёт `InvalidFindings("malformed id")` → −1. Среда же открывает эпизод с любыми ID (`ReadOnlyStore` и
`get_record` формат не проверяют), т.е. агент видит записи, на которые ответить корректно невозможно.

**Воспроизведение.** `audit/a_jury_rename.py` имитирует harness жюри: биективно переименовывает все ID эпизода
`dev/ep_053daf06ab62f121` в заданный формат, переставляет строки всех таблиц, пересчитывает хэши manifest, кладёт эпизод
через `episode_ref` и отправляет (а) ответ «их oracle» по переименованному эталону обычным `submit` после двух
`get_record`, (б) наш oracle процесса оценщика.
```
$ python3.11 -I audit/a_jury_rename.py .

UUID без скобок                    eid как есть                    0.996       1.000  ok
UUID в фигурных скобках            eid как есть                   -1.000      -1.000  ok

слэш ('INV/2026/000123')           eid как есть                   -1.000      -1.000  ok
```

На всех 20 открытых эпизодах формат «слэш» даёт −1 на каждом нечистом эпизоде (14/14), а `control`/UUID — 1.0
(0.996 с двумя шагами осмотра).

**Пункт PDF.** 06: «Ещё 20 парных проверок меняют порядок и ID»; 10: «перестановка и смена ID сохраняет ответ oracle и
награду с учётом новых ID» (15 баллов). Формат новых ID выбирает жюри; номера вида `INV/2026/0001` обычны в учёте.

**Фикс.** ID в выводе допустим, если проходит `ID_RE` **или существует в открытых записях эпизода** (row_id, invoice_id,
payment_id, doc_id, entity_id; множество строит процесс оценщика при `open` из тех же открытых файлов). Остальное без
изменений: неизвестный ID странного формата и Unicode-двойник по-прежнему −1, неизвестный ID обычного формата — FP.
**Риск:** минимальный. Для всех наших эпизодов все ID проходят `ID_RE`, поэтому поведение и награды побайтово прежние;
существующий тест `affected_ids=["../../grader_data/truth.json"] → −1` остаётся в силе. Правило совпадения (`is_match`) и
формула награды не меняются; меняется только проверка структуры для ID, которые реально есть в эпизоде.
Отвергнутая альтернатива — «любая печатная строка ≤128»: она меняет исход существующих атакующих тестов (−1 → FP).

### F2. `episode_id` длиной 65–128 даёт −1 за любой ответ

`findings.schema.json`: `episode_id.maxLength = 64`; `manifest.schema.json` и `truth.schema.json` допускают `episode_id`
до 128 символов. Если жюри переименует `episode_id` (например, `<старый>__perm__<uuid>`, 70 символов), то даже пустой
ответ на чистом эпизоде — неверная структура.

**Воспроизведение.** Строка `eid 65 символов` в выводе F1; на всех 20 эпизодах −1, включая 6 чистых
(`schema: $.episode_id: string too long`).

**Пункт PDF.** 06, 10 (смена ID), 05 «Неверная структура» должна означать неверную структуру, а не длину чужого ID.

**Фикс.** `findings.schema.json`: `episode_id.maxLength` 64 → 128 (как в manifest/truth). **Риск:** только расширение
принимаемого; для наших эпизодов (`ep_` + 16 hex = 19 символов) ничего не меняется; сравнение `episode_id` с эталоном
остаётся строгим.

### F3. Глубоко вложенный `submit` роняет среду или оставляет эпизод без оценки

`AuditEnv.step` проверяет размер findings через `json.dumps(findings)` и ловит `RecursionError`, но затем
`GraderClient.call` сериализует запрос с запасом в 2–3 уровня, а оценщик разбирает его ещё глубже по стеку. В узком окне
глубины первая сериализация проходит, а следующая падает.

**Воспроизведение (in-process).**
```
$ python3.11 -I audit/b_deep_sweep.py .      # глубина 1..1200, действие dict и строка JSON
RecursionError из env.step: [('dict', 989), ('dict', 990), ('dict', 991), ('dict', 992), ('str', 989)]
награда != -1 (эпизод не оценён): [('dict', 985, 0.0), ('dict', 986, 0.0), ('dict', 987, 0.0), ('dict', 988, 0.0), ('str', 985, 0.0), ('str', 986, 0.0), ('str', 987, 0.0), ('str', 988, 0.0)] ... всего 8
терминальных submit: 2184 | записей graded/invalid_findings у оценщика: 2176
```
В неоценённых случаях оценщик пишет только `internal_error`; эпизод завершён (`terminated=True`), награда 0.0 вместо −1,
в `results` его нет (в `jury_run` — «оценено N из M», в `agent_host` — exit 3).

**Воспроизведение (внешний агент — граница изоляции).** Агент присылает одну строку JSON:
```
$ for d in 984 985 986; do python3.11 -m auditenv.agent_host --agent-cmd "python audit/agents/deep_agent.py $d" --split dev --mode train --grader-log /tmp/ah.jsonl --agent-stderr /tmp/ah_err.log > /tmp/ah_out.json; echo "d=$d exit=$?"; done
d=984 exit=0        # 10 эпизодов оценены, −1
RecursionError: maximum recursion depth exceeded while encoding a JSON object
d=985 exit=1        # трейсбек, итогов нет ни по одному эпизоду
d=986 exit=0        # строка не разбирается: invalid_json, шаг израсходован (верно)
```

**Пункт PDF.** 04: «Неизвестный ID или действие даёт ограниченную ошибку и расходует шаг»; 05: «Неверная структура.
Завершает эпизод с наградой -1 и ошибкой в журнале оценщика»; 10 «Контракт и изоляция … неверного ввода».

**Фикс.** В `AuditEnv.step`, ветка `submit`: до сериализации — итеративная (без рекурсии) проверка глубины findings,
предел 32 уровня (корректный findings имеет глубину 4). Глубже → `{"__invalid__": "too_deep"}`, т.е. ровно тот же путь,
что уже используется для `too_large`/`not_serializable`: −1 и `invalid_findings` в журнале. **Риск:** низкий. Исход
меняется только для findings глубже 32, где раньше была та же −1 по схеме, падение или неоценённый эпизод. Награда,
matcher и схемы не трогаются.

### F6. `oracle_from_truth` требует имя каталога = `episode_id`
`OracleFromTruth.reset` ищет `<truth_dir>/**/<episode_id>/truth.json`. В сценарии F5 (каталог `e1`):
```
$ python3.11 -m auditenv.cli run --trusted --policies oracle_from_truth --truth-dir myroot/grader --splits perm …
FileNotFoundError: oracle_from_truth: нет truth.json для ep_053daf06ab62f121 в myroot/grader
```
**Фикс:** если по имени каталога не найдено, искать `truth.json` с этим `episode_id` внутри. Ветка срабатывает только там,
где раньше было исключение. Не затрагивает matcher, награду и генератор.

сдаваемый `trajectories.jsonl` (и `grader_data/run_summary.json`). **Фикс:** в примере — `--trajectories their_traj.jsonl`.

### F12. Логирование глубокого действия в `cli run`
`runner.run_episode` сериализует `action` для траектории; in-process политика, вернувшая действие глубже ≈990 уровней,
роняет `cli run` (до и после F3). In-process политики — доверенный код (DESIGN §7), жёсткая граница — `agent_host`,
который пишет строку агента как есть. **Не исправляется.**

### F13. Размер наблюдения
Явного лимита байт нет, но наблюдение ограничено структурно: ≤50 строк страницы, запись счёта ≤909 Б, документ ≤≈1.1 КБ.
Худший размер компании (`audit/b_contract.py`): страница invoices ≤33 959 Б, ledger ≤11 597 Б, первое наблюдение 6.9 КБ;
в 2111 строках `trajectories.jsonl` максимум 34 129 Б. **Не исправляется.**

### F14. ID длиннее 128 символов
`get_record`/`get_document` отвергают ID >128 (`invalid_arguments`), `findings` — `maxLength 128`: эпизод с такими ID
нерешаем (строка «длина 129» в F1). Реалистичные форматы, включая UUID (36), короче. **Не исправляется**, лимит
документируется в README.

### F15. `reset` посреди эпизода
Повторный `reset` изолирует состояние (новый эпизод, 100 шагов, старые курсоры не нужны), но брошенный эпизод не
оценивается и не попадает в `results`. Gymnasium это допускает; превращать брошенный эпизод в truncation значит менять
контракт. **Не исправляется**, документируется.

## Гипотезы (без воспроизведения — не в список на исправление)

* `seed` типа `numpy.int64`: `GraderClient.call` → `json.dumps` даст `TypeError` до проверки seed. В stdlib-окружении
  numpy нет, воспроизвести нечем; `int(seed)` на стороне harness — их ответственность.
* Harness жюри, который «вслепую» переименует и строки `fx:<date>:<src>:<tgt>` в эталоне, получит FN по FX: `fx_id`
  выводится из содержимого `fx.csv`. Описано в README (F5); наш эксперимент с переименованием по ID-столбцам таблиц
  сохраняет все 24 FX-доказательства.
* In-process политика, зависшая внутри `act()` навсегда, не прерывается (лимит времени проверяется на следующем `step`).
  Замедленная политика корректно получает `truncated_time` (см. C), вечная — только через `agent_host --time-limit-s`.

## Проверено без проблем

**A. Harness жюри.**
* `fx_id` после перестановки строк `fx.csv` и переименования ID: на 20 эпизодах все 24 issue с FX-доказательствами
  совпадают, `get_record(fx, fx_id)` работает (`fx_id` — содержимое, не ID).
* Хэши manifest после ручной перестановки: среда их не проверяет и эпизод открывает (oracle = 1.0); проверяет только наш
  валидатор (`manifest hash mismatch`) — ожидаемо, описывается в README (F5).
* UUID без скобок, длина 64–128, нижний регистр, другой `episode_id` (UUID) — честный ответ сохраняет награду.
* Запятые/кавычки в ID в `ledger.csv` экранируются модулем `csv`; `get_record` находит запись.

**B. Контракт** (`audit/b_contract.py`).
* seed `0`, `1`, `2**63−1`, `2**63`, `2**64`, `2**64+1`, `−1`, `−2**70`, `10**400`: эпизод открывается, повтор seed даёт
  тот же `episode_id`; `None` — счётчик объекта (как в DESIGN); `True/False/1.5/1.0/"42"/[1]` →
  `EpisodeOpenError: seed: ожидается целое число`.
* `step` до `reset` → `not_reset`, без исключения; повторный `reset` посреди эпизода → новый эпизод, `steps_remaining`
  с 100; повторный `submit` → `episode_finished`, без переоценки.
* Все 2111 строк `trajectories.jsonl`: JSON без NaN/Inf, `terminated & truncated` = 0, награда `float` в [−1, 1].
  Живые `obs/info` на худшем размере: round-trip `json.loads(json.dumps(x)) == x` без расхождений, награда `float`.
* Калькулятор: нестрока, `**`, `//`, имена, вызовы, длина >256, >64 узлов → `calc_error`.

**C. Лимиты** (`audit/c_limits.py`).
* Границы size в config соблюдаются с понятной ошибкой (`n_invoices` 76, `n_expenses` 701 и т.д. → `EpisodeOpenError`).
* Худший размер (до 1875 проводок, 195 документов, 12 ошибок) + 99 самых тяжёлых действий + submit 30×10 ID с
  объяснениями по 1000 символов: `reset` ≤0.13 с, эпизод ≤0.01 с, пик RSS ≈23 МиБ (среда) / ≈24 МиБ (оценщик).
* In-process политика, «думающая» дольше лимита: следующий `step` → `truncated=True`, оценщик пишет
  `truncated_time`, пустой ответ (проверено с лимитом 1 с).
* Размер решения: дерево 20 МБ, `.git` 17 МБ — далеко от 1 ГБ.
